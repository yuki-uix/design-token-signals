# 冲突判定规则表

> 这张表回答一个问题：**什么算冲突？**
>
> `README.md` 里那句「token 选择在不同轴上拉向相反方向就是冲突」是立场，不是判据——
> 它无法判定任何一个具体界面。这份文档把它变成可以被一个人、或一段程序无歧义执行的规则。

规则的依据来自本仓库 9 套主题的 `meta.antiCases` 和 `meta.rationale`。
每套主题声明了「我不适合用在哪」，那些声明反过来就是冲突的边界。
每条规则都注明了它来自哪一套，没有凭空发明的判断。

---

## 先读这一节：测量口径

**这一节不是背景说明，是规则的一部分。** 下面每条规则的触发条件都依赖这里的定义。
这些口径不是推演出来的，是在三个真实站点上跑探针撞出来的——具体见文末「验证记录」。

### 字体类别

只看 `font-family` 的**第一个** family 名，并且**必须先排除 `sans-serif`**。

直接用 `/serif/` 匹配整个字体栈会把 sans 误判成 serif：ia.net 的字体栈是
`iASansDay, system-ui, -apple-system, sans-serif, ...`，一个纯 sans 的站点，
用 `/serif/` 匹配整栈会命中 28 次衬线、0 次无衬线，**判定结果与事实完全相反**。

字体类别只能作为弱证据。名字里没有 serif/sans 的自定义字体（iASansDay、ABC Favorit、
Space Grotesk）无法用名称判定，此时应跳过依赖字体类别的规则，而不是猜。

### 颜色解析

**必须光栅化，不能用正则从颜色字符串里抠数字。**

实测 gumroad.com 的链接描边是 `oklch(0.872 0.01 258.338)`。朴素正则把 L=0.872 当成 R、
C=0.01 当成 G、**H=258.338 当成 B**，产出非法的 `#0100102`（七位），
并伪造出一个 `h240 s100` 的高饱和幽灵色，在 102 个元素上出现，直接顶掉了真正的品牌色。

正确做法是把颜色画进 1×1 的 canvas 再读回 sRGB 字节，对 `oklch` / `lab` / `color()` /
`hwb` 全部正确。上面那个 oklch 的真实颜色是 `#d1d5dc`——一个浅灰，饱和度低到根本不会被
当成 accent。

无法被浏览器接受的颜色值要计数并报告（`unparsedColors`），不能静默跳过。

### 阴影解析

**必须先剥掉颜色函数再取长度值。**

`box-shadow` 的颜色可以写在前面，而 `rgba(0, 0, 0, 0.25) 0px 2px 32px 0px` 里
最先出现的三个数字是颜色通道。直接取第三个匹配当 blur，会把这条的 blur 读成 `0` 而不是 `32`。

这个缺陷造成两个方向相反的错误：R-09 在一个没有硬阴影的站点上误报，
R-03 的 brutalist 豁免对所有站点生效因而永不触发。两边都是静默的。

判定口径：
- **硬阴影**：blur = 0 **且** 偏移量至少有一个 ≥ 2px。`0 0 0 1px` 是描边环，不是硬投影，单独计数。
- **柔和阴影**：blur ≥ 6px
- alpha < 0.08 的阴影不表达任何语汇，排除
- 焦点态（`:focus` / `:focus-visible` / `:focus-within`）的阴影排除

解析逻辑有定点测试：`conflicts/test/parse-shadow.test.mjs`，`node` 直接跑。

### 饱和度

**只在明度 L ∈ [18, 88] 区间内判定饱和度，区间外一律不判定。**

HSL 的饱和度在极端明度下会失真：`rgb(1, 0, 16)`（肉眼是纯黑）的计算饱和度是 **100%**。
不加明度护栏的话，任何深色文字都会被当成「高饱和 accent」。
gumroad.com 的探针第一轮就把近黑色 `#010010` 排到了高饱和色的第一位，出现 102 次。

饱和度还要 clamp 到 100——浮点误差会算出 103 这种值。

### 面积

**`coverage` 是视口内并集覆盖率，不是盒面积累加。**

旧实现是把每个带该背景色的元素的盒面积直接相加再除以视口面积，既不裁剪视口、也不去重叠。
gumroad.com 上的 6 个 `#ffc900` 元素**全部位于首屏之外**，真实首屏覆盖率是 **0**，
旧算法报 **0.513**。规则写的是「覆盖首屏可见面积」，测的却完全是另一个量，
而且它不会报错，只会给出一个看起来合理的数字。

现在的算法：先把每个矩形裁进视口，再按 8px 网格求并集。
网格量化会略微高估（误差上界是一个网格边长，400×300 的矩形高估 1.3%），
这个方向是安全的——宁可多报一点，不要漏。

计算逻辑有定点测试：`conflicts/test/coverage.test.mjs`，其中一条专门回归
「六层同色堆叠，累加会得到并集的 5.9 倍」。

### 圆角

分桶统计，**pill 必须单列，不能并进数值桶**。

`border-radius: 9999px` 的计算值是 `1.67772e+07px`。gumroad.com 的按钮里 115 个是 pill，
如果按数值比较，它们会全部落进「圆角 ≥ 16px」，被判成「强亲和信号」——
而 pill 是一套独立的形状语汇，与「大圆角」表达的不是同一件事。

**一个站点通常没有单一圆角值。** linear.app 的按钮分布是 0px×50 / pill×41 / 5-12px×19，
三个桶都不可忽略。规则里说「圆角」时，指的是**占比最高的那个桶**；
**如果最高桶占比不足 50%，依赖「主圆角桶」的规则（R-01、R-03、R-07、R-08）一律不判定，
先报告「该界面没有统一的形状语言」。** 这不是建议，是前置条件——linear.app 实测
`dominantShare = 0.41`，此时拿 `0px` 当作「这个站的圆角」去判冲突，结论没有意义。

### accent 的识别

**不能按出现频次取。** gumroad.com 出现最多的按钮背景色是 `#ffffff`（105 次），
而它真正的品牌色是粉色 `#ff90e8`，在采样里只出现 **1 次**。

accent 的识别顺序：
1. CSS 自定义属性里名字含 `accent` / `primary` / `brand` 的颜色值
2. 主 CTA（页面首屏最显著的按钮）的背景色
3. 明度区间内饱和度最高、且出现在交互控件上的颜色。
   **同分时背景色优先于描边色**——accent 是被「用上去」的，不是勾出来的边。

三步都取不到时，`accent.source` 为 `none`，**依赖 accent 的规则（R-02、R-03、R-05、R-07）
必须报告「无输入、无法判定」，不得判为「未发现冲突」。**

### 统计范围

**只统计交互控件与内容区域，不统计装饰性插画、渐变背景、品牌动画。**

linear.app 在明度区间内有四种高饱和色（粉 #f79ce0 用了 90 次、橙 #f7bf8b 44 次、
蓝紫 #8fa6ff 32 次、黄 #ffdf9f 20 次）。若把它们全算作 accent，
R-06 会立刻判定「用量失控」——但那些颜色绝大部分来自首屏的装饰图形，不是 UI 控件。

### 字重

可变字体会产生 510、590 这样的字重值（linear.app 实测），
**不要用 600 / 700 / 800 这样的等值比较**，一律用区间：
`≤ 550` 为中性，`551–690` 为强调，`≥ 691` 为表达性字重。

## 强度定义

| 强度 | 含义 |
|---|---|
| **强** | 两个轴指向明确相反，且都落在该轴的端部。几乎不可能是有意为之。 |
| **弱** | 方向相反但至少一个轴在中段。可能是有意的张力，报告但不建议必改。 |

## 规则

### R-01 · 形状亲和 × 阅读密度

- **轴**：Form × Typography
- **触发**：主圆角桶为 `13-24px` 或 `>24px`（**前置：`hasUnifiedShapeLanguage` 为真**），且正文 `line-height / font-size ≤ 1.45`
- **强度**：强
- **依据**：`warm-organic` 的 rationale 写的是「16px 大圆角**和**宽行距营造放松节奏」——
  这两个 token 在设计上是配套的。它的 `antiCases` 明确排除「需要高密度信息展示的后台」。
  大圆角说「慢下来、有呼吸」，紧行距说「塞满、快读」。
- **典型误判**：
  移动端卡片布局。卡片容器需要大圆角（触控友好 + 视觉分组），
  而卡片**内部**是数据列表，必须紧凑。
  此时圆角属于容器层、行距属于内容层，**不在同一层级，不构成冲突**。
  判定前先确认两个 token 作用在同一层级的元素上。

### R-02 · 机构色 × 表达性字重

- **轴**：Color × Typography
- **触发**：accent 色相 ∈ [200, 250]（蓝）且饱和度 < 60%，同时标题字重 ≥ 691
- **强度**：弱
- **依据**：`corporate-blue` 的 `antiCases` 是「面向年轻消费者的产品 / **创意类或个性化品牌**」——
  低饱和蓝的适用域明确排除了个性表达；其 rationale 补充说这套配色的目的是
  「避免任何视觉意外」，字重用 600。反过来 `playful` 用 800 字重配高饱和紫，
  它的 `antiCases` 是「**企业采购决策场景** / 合规安全类产品」。
  两套主题的不适用域正好互为镜像：低饱和蓝在说「不会有意外」，≥691 的字重在说「看我」。
- **典型误判**：
  B2B 落地页的 hero H1 用超粗字重是**版面层级**需要，不是品牌信号。
  判定时看重字重是否**扩散到了正文小标题**；若只出现在单一 hero 元素上，不算冲突。

### R-03 · 锐角正式 × 高亮警示色

- **轴**：Form × Color
- **触发**：主圆角桶为 `0px` 或 `1-4px`（**前置：`hasUnifiedShapeLanguage` 为真**），且 accent 在明度区间内饱和度 ≥ 85% 且明度 ≥ 70%（高亮色）
- **强度**：弱
- **依据**：`monochrome` 的 `antiCases` 是「**需要多色彩表达品牌活力的产品** /
  信息架构复杂的管理后台」，它用 2px 圆角配纯黑 accent，rationale 说这是
  「接近无圆角，强调正式感」——锐角与高饱和亮色在它的适用域里是互斥的。
  `corporate-blue` 的 `antiCases`「面向年轻消费者的产品」指向同一边界。
- **典型误判（本表最重要的一条）**：
  **neo-brutalist 风格正是 0px 圆角 + 高饱和亮色**（本仓库该主题的 accent 是 `#f5e100`，
  饱和度 100%）。这是有意的反设计立场，不是失误。

  判定前必须先排除 brutalist 语汇。判据是**同时**满足以下两条中的至少一条：
  - 存在 blur 为 0 的硬阴影（如 `4px 4px 0 #000`）
  - 存在 ≥ 2px 的纯黑描边（`border` 或 `outline`）

  **注意：不要用品牌名反推语汇。** gumroad.com 常被当作 brutalist 的代表，
  但实测它当前首页在前 4000 个元素上**一个 `box-shadow` 都没有**。
  按「它是 Gumroad 所以一定有硬阴影」去判定会得出错误结论。

### R-04 · 衬线人文 × 暗底工具感

- **轴**：Typography × Color
- **触发**：标题与正文首选字体为衬线（按「测量口径」判定），且页面背景明度 < 20%
- **强度**：弱
- **依据**：`minimal-dark` 的 `antiCases` 是「面向普通消费者的产品 /
  **需要暖色调或亲和感的品牌**」——暗底工具语汇的适用域明确排除了亲和感，
  而衬线正是亲和与人文的载体。反向看，`warm-organic` 的 rationale 是
  「米白暖底色 + 橙棕 accent + 衬线字体，创造纸质质感」，其 `antiCases`
  「**需要高密度信息展示的后台**」同样把它挡在工具型暗底产品之外。
  本仓库两套衬线主题全为亮底，三套暗底主题全部用 Inter，无一例外。
- **典型误判**：
  阅读类产品的**夜间模式**。此时暗底是功能性适配，不是品牌信号，衬线保持不变是正确的。
  判定前检查是否存在亮色变体（`prefers-color-scheme` 媒体查询、主题切换器）；
  若暗底只是 dark mode 的一种状态，不适用本规则。

### R-05 · 底色色温 × accent 色温

- **轴**：Color × Color
- **触发**：背景 `R − B > 6`（暖底）且 accent 色相 ∈ [200, 260]（冷）；或背景 `B − R > 6`（冷底）且 accent 色相 ∈ [20, 50]（暖）
- **强度**：弱
- **依据**：`warm-organic` 米白暖底 `#fafaf8` 配暖橙 `#e8643a`，
  `clean-light` 冷灰白 `#f6f9fc` 配冷蓝紫 `#635bff`——两套都是同温搭配。
  边界由 `antiCases` 划定：`warm-organic` 排除「**金融/合规类产品**」，
  `minimal-dark` 排除「**需要暖色调或亲和感的品牌**」。
  冷与暖各自有明确的不适用域，混温等于同时踩进两边。
- **典型误判**：
  **阈值必须是 6，不能更低。** gumroad.com 的背景 `#f4f4f0` 实测 `R − B = 4`，
  肉眼几乎不可辨，属于纸感微调而非色温声明。
  把阈值放到 3 以下会让大量中性灰白背景被误判为「暖底」。

  另一个误判来源：**品牌印象会骗人。** ia.net 是「温暖的写作工具」的典型代表，
  实测背景 `#f7f7f7`，`R − B = 0`，完全中性。**判定必须基于实测值，不能基于品牌气质。**

### R-06 · accent 用量失控

- **轴**：Color（单轴内部的用量维度）
- **前置**：该颜色必须**至少出现在 1 个交互控件上**（`onControl ≥ 1`）。
  只出现在版面色块上的高饱和色是品牌区块背景，不是 accent，本规则不适用。
- **触发**（满足任一）：

  | | 判据 | 强度 | 标定它的页面 |
  |---|---|---|---|
  | **(a) 角色扩散** | `roleCount ≥ 2` **且** `tagCount ≥ 3` | **强** | `fixtures/r06-positive.html` |
  | **(b) 面积失控** | `coverage ≥ 0.25` | **弱** | `fixtures/r06-area.html` |

  `coverage` 是**视口内并集覆盖率**，不是盒面积累加——两者差别极大，见「测量口径 · 面积」。

- **为什么 (a) 是强、(b) 是弱**：角色扩散意味着 accent 同时在背景、文字、描边上出现，
  它已经不再承担「指出重点」的功能，这几乎总是失控。而大面积铺陈在营销落地页上
  可能是有意的品牌表达（全幅 hero 是常规做法），所以 (b) 只作提示，需人工确认。
- **依据**：`monochrome` 的 `antiCases` 是「需要多色彩表达品牌活力的产品 /
  信息架构复杂的管理后台」——它用纯黑白换来的「自信」，代价正是放弃色彩的表达力，
  说明色彩用量本身是有预算的。`bold-dark` 的高饱和红服务于「制造强烈对比」，
  而它的 `antiCases`「企业合规类产品 / 医疗金融等需低调可信形象的场景」表明：
  高饱和本身就是一种有代价的声明，**对比的前提是稀有**。
- **典型误判**：
  1. **不要用出现次数判定。** 初版触发条件写的是「出现在 ≥5 个不同语义位置」，
     实测发现「语义位置」既无枚举也无边界，探针唯一的代理是标签名——
     linear.app 上命中最多的 `#f79ce0` 出现 45 次，却是 `roleCount = 1`、`tagCount = 1`，
     全是 `span`。一个把 accent 同时用在 CTA、链接、图标、边框、徽章上的设计系统，
     只要这些都渲染成 `span`，旧写法照样不触发。
  2. **也不要把阈值顶到上限。** 第二版把 (a) 写成「≥3 种角色」，而角色集合总共就三种
     （背景 / 文字 / 描边），等于要求三种同时出现——换了一种永不触发。
     现在的 `≥2` 是拿正负例标定出来的，不是猜的。
  3. **(b) 会在全幅品牌 hero 上触发。** `fixtures/r06-area.html` 的紫色覆盖 49.2% 视口，
     这在营销落地页上是常规设计。所以 (b) 判为弱，结论里必须写明这可能是有意为之。
  4. 装饰性图形不计入（见「测量口径 · 统计范围」）。
  5. 设计系统的 token 定义文件会列出 accent 的所有变体，那是**定义**不是**使用**。
- **标定数据**：见「验证记录 · 第三轮」。四个页面的分离度足够宽，
  正例 `tagCount = 8` 对负例 `1`，面积例 `coverage = 0.492` 对负例 `0.004`。
- **关联案例**：`case-03-minimal-meets-decorative`

### R-07 · 大圆角 × 合规语境

- **轴**：Form × Color
- **触发**：按钮、输入框、卡片这类**高频小元素**的主圆角桶（探针的 `radiusSmallElements`）≥ `13-24px`，
  且该分布的 `hasUnifiedShapeLanguage` 为真，
  且 accent 色相 ∈ [200, 240] 且饱和度 < 60%
- **强度**：弱
- **依据**：`corporate-blue` 的 rationale 是「极小圆角(4px)，传递可预期性和机构感」，
  其 `antiCases` 排除「创意类或个性化品牌」；`playful` 24px 圆角的 `antiCases`
  排除「合规/安全类产品」。两端在本仓库的主题定义里是明确互斥的。
- **典型误判**：
  modal、drawer、sheet 这类**大容器**用 16px 圆角是当代通用样式，不承载品牌信号。
  只统计按钮、输入框、卡片；大容器排除在外。

### R-08 · 渐变未来感 × 传统信任

- **轴**：Color × Form/Typography
- **触发**：accent 为多色停靠点的渐变，且**渐变进入了 UI 控件**（按钮背景、边框、文字填充），
  同时主圆角桶 ≤ `1-4px`（`hasUnifiedShapeLanguage` 为真）或首选字体为衬线
- **强度**：强
- **依据**：`ai-gradient` 的 `antiCases` 写得很直白：
  「需要建立长期信任的传统行业 / 日常工具类产品（**gradient 疲劳风险**）」，
  其 rationale 强调「与 minimal-dark 的区别在于**动感**而非静止」。
  渐变说「我们在往前冲」，锐角与衬线说「我们已经在这里很久了」。
- **典型误判**：
  渐变仅用于 logo、单张插画或 hero 背景，**未进入任何 UI 控件**时不判定——
  那是品牌资产，不是界面语汇。

### R-09 · 阴影语汇混用

- **轴**：Form × Form
- **触发**：同一界面同时存在 blur = 0 的硬阴影（≥ 2 处）与 blur ≥ 6px 的柔和阴影（≥ 2 处）
- **强度**：强
- **依据**：`neo-brutalist` 唯一独有的 token 是 `--shadow-md: 4px 4px 0 #000`，
  rationale 是「纯黑描边阴影…拒绝视觉粉饰」；而它的 `antiCases` 是
  「企业销售场景 / **需要第一印象建立信任的 B2B 产品**」——
  硬阴影语汇有明确且狭窄的不适用域。柔和阴影恰恰是它拒绝的那种粉饰。
  一个界面同时用两者，等于同时声明「我拒绝粉饰」和「我很精致」。
- **典型误判**：
  硬阴影仅用于 `:focus-visible` 的焦点环时不判定——那是可访问性需要，不是装饰语汇。
  判定时排除所有焦点态、选中态的阴影。

### R-06 的标定数据

QA 的要求是「先找到确凿会触发 R-06 的页面，再反过来定阈值」。
`conflicts/fixtures/` 下的三个页面版面完全相同，**唯一变量是 accent 的用量**：

|---|---|---|---|---|---|---|
| `r06-positive.html`（角色扩散） | 3 | 8 | 6 | 0.110 | 触发 (a) | ✅ |
| `r06-area.html`（面积失控） | 2 | 2 | 1 | **0.492** | 触发 (b) | ✅ |

### F3 带来的一个后果，以及对上一轮结论的更正

可见性判据上线后，linear.app 的 CTA 候选名单**变成空的**——那个跳转链接是它唯一的候选。
于是 accent 落到第 3 步，而该站所有高饱和色的 `onControl` 都是 0，
最终 **`accent.source = 'none'`**，R-02/R-03/R-05/R-07 在 linear.app 上报「无法判定」。

这不是退步，是诚实：之前那个 `#5e6ad2` 是从一个隐藏元素上取到的。

因此上一轮写下的「实测确认 Linear 的主 CTA 正是 `#5e6ad2`，与 `minimal-dark` 声明一致」
**需要更正**——那个值的来源本身就是 F3 描述的运气。`#5e6ad2` 与本仓库主题声明一致这件事
仍然成立（可在 DevTools 里人工确认），但**它不再是探针验证过的结论**。

### 仍未解决

1. **自定义字体无法按名称判定衬线**。gumroad.com（ABC Favorit）、linear.app（Inter Variable）、
   ia.net（iASansDay）三个站的 `fontClasses` 全是 `unknown`，**R-04 在这三个站上都无法判定**。
   当前处理是跳过而不是猜。若 `#47` 的冒烟验证显示这是主要阻碍，需换成字形度量判定
   （比较 x-height / cap-height 或检测笔画末端），而不是放宽规则。
2. **主 CTA 在「没有彩色按钮」的站点上识别不出来**。F3 修好了误选隐藏元素的问题，
   但 linear.app 这类首屏没有实心彩色 CTA 的站点，第 2 步会返回空，
   第 3 步又要求颜色出现在交互控件上——最终 `accent.source = 'none'`。
   目前的处理是如实报告「无法判定」，不猜。若 `#47` 显示这类站点占比很高，
   需要引入第 4 个来源（例如取首屏内面积最大的非中性色块的颜色），而不是放宽前三步。
3. **R-01、R-02、R-09 仍未被正向触发过**，只验证了不误报。R-06 本轮已用构造页面正向验证，
   这三条还没有。需要的是像 `fixtures/r06-*.html` 那样的一组定点页面，
   而不是继续在真实站点上碰运气——真实站点给的是负例，正例得自己造。
4. **网格量化会高估覆盖率**（400×300 高估 1.3%）。方向是安全的（宁可多报），
   但如果将来把 `coverage` 用在需要精确值的地方，要换成扫描线求并集。
